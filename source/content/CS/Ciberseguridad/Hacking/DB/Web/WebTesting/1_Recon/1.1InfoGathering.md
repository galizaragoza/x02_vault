# Fingerprint web server
El objetivo de esta fase es identificar el tipo y versión del servidor web que aloja la web del objetivo. Esto ayuda a empezar a mapear la infraestructura, conocer las tecnologías que se utilizan y en algunos casos hallas las primeras vulnerabilidades, si las versiones del software están desactualizadas.
## Metodología
El proceso esta muy automatizado, pero es necesario comprenderlo. Haciendo requests a un servidor web con herramientas como [[telnet]] (HTTP) u [[OpenSSL]] (HTTPS) se puede analizar la respuesta y sus headers para identificar el servidor, esta técnica se llama Banner Grabbing.

```
HTTP/1.1 200 OK
...
Server: Apache/2.4.41 (Unix) <-- EL SERVIDOR ES REVELADO POR LA PROPIA RESPONSE
...
```

En este ejemplo el tipo y versión están claramente expuestos, sin embargo un sitio seguro oculta esta información modificando los `Header` de las respuestas, en ese caso se pueden utilizar otras técnicas para fingerprintear el webserver.
### Orden de los headers
- Fijándose en el orden en que los headers aparecen en la respuesta se puede identificar el software que está corriendo
### Sending malformed requests
- Enviando peticiones intencionalmente mal formadas, se pueden analizar los errores que nos envía el servidor como respuesta, en páginas más inseguras incluso se puede renderizar en el navegador la página de error default del software.

```
GET / BOGUS/1.1 <-- Enviando una solicitud a un recurso inexistente


HTTP/1.1 400 Bad Request
...
Server: Apache/2.4.41 (Unix) 
...
```

## Tools
[Netcraft](https://sitereport.netcraft.com/), [[!nikto]], [[Nmap]]


# Webserver Metafiles
Esta fase pretende encontrar rutas y/o funcionalidades ocultas u ofuscadas mediante el análisis de metafiles, además de añadir cualquier otra información que permita comprender mejor el sistema objetivo.

## robots.txt
El archivo `robots.txt` es una convención que indica a los web crawlers que no deben indexar ni analizar determinadas rutas o archivos

```
User-agent: * <-- Indica a todos los crawlers (User-Agent: Googlebot desactivaría solo el de Google) 
Disallow: /search <-- Indica a los crawlers que recursos están prohibidos
Allow: /search/about <-- Indica los recursos permitidos
Allow: /search/howsearchworks
Disallow: /sdch
```

Por ejemplo, usando [[curl]] o [[wget]] se puede consultar el archivo `robots.txt` de ejemplo.com

```
curl -O http://ejemplo.com/robots.txt
```

Se puede lograr lo mismo con operadores de búsqueda en distintos navegadores mediante [Google Webmaster Tools](https://search.google.com/search-console/welcome?hl=en).

## META tags
Las `<META>` tags se ubican en cada sección `HEAD` de un documento html, y deberían ser consistentes a través de toda la web por si un crawler comenzase en cualquier punto que no sea el webroot (`/`)

```html
<meta name="google-site-verification" content="iT3tOfJrBhsTViDYakVkAKwpkh6fC7c_-tYGMNeIJH4" />
<meta http-equiv="X-UA-Compatible" content="IE=Edge" />
<meta name="GENERATOR" content="Microsoft SharePoint" />
<meta name="progid" content="SharePoint.WebPartPage.Document" />
<meta http-equiv="Content-Type" content="text/html; charset=utf-8" />
<meta http-equiv="Expires" content="0" />
<meta http-equiv="X-Frame-Options" content="SAMEORIGIN" />
<meta http-equiv="X-XSS-Protection" content="1;mode=block" />
<meta http-equiv="X-Content-Type-Options" content="nosniff" />
<meta name="viewport" content="width=device-width, initial-scale=1.0" />
<meta name="theme-color" content="#958e6e" />
<meta name="keywords" content="Página oficial de la Casa de Su Majestad el Rey de España. Información e imágenes sobre la actividad de la Familia Real española y la Casa de S.M. el Rey" /><meta name="description" content="Casa Real" />
<meta name="titulo" content="Casa Real" />
```

Este es un ejemplo de las META tags de www.casareal.es.

## Sitemaps
Un sitemap es un archivo donde los desarrolladores presentan información sobre la estructura de una web: Páginas, videos, archivos... Y las relaciones entre ellos.
Esto permite a los crawalers escanear la página de forma más eficiente, un tester puede aprovechar el archivo `sitemap.xml` para continuar perfilando la infraestructura.

```xml
<urlset xmlns="http://www.sitemaps.org/schemas/sitemap/0.9">
<url>
	<loc>http://www.psoe.es</loc>
	<lastmod>2017-09-05</lastmod>
	<changefreq>weekly</changefreq>
	<priority>1</priority>
</url>
<url>
	<loc>http://www.psoe.es/transparencia/</loc>
	<lastmod>2015-01-23</lastmod>
	<changefreq>weekly</changefreq>
	<priority>1</priority>
</url>
<url>
	<loc>http://www.psoe.es/propuestas/</loc>
	<lastmod>2015-07-20</lastmod>
	<changefreq>weekly</changefreq>
	<priority>1</priority>
</url>
...
```

Por ejemplo, un fragmento del archivo sitemaps de www.psoe.es.

## Security file
El archivo `security.txt` es un estándar propuesto en el cual se pueden recoger las políticas de seguridad de una organización X, si está presente, puede contener información como: Nuevas rutas o ubicaciones que pueden ser interesantes, información open source digna de ser recopilada, información sobre bug bounties... 

Este archivo puede encontrarse o bien en la raíz o en el dir `.well-known/`
- `www.ejemplo.com/security.txt`
- `www.ejemplo.com/.well-known/security.txt`
- 
Por ejemplo, el de LinkedIn

```txt
Contact: mailto:security@linkedin.com
Contact: https://www.linkedin.com/help/linkedin/answer/62924
Encryption: https://www.linkedin.com/help/linkedin/answer/79676
Canonical: https://www.linkedin.com/.well-known/security.txt
Policy: https://www.linkedin.com/help/linkedin/answer/62924
```

## Humans file
El archivo `humans.txt` es una suerte de "créditos" en los que se da reconocimiento a las personas que han trabajado en una web, si existe, puede ser utilizada para recopilar OSINT que puede ser útil en SE (social engineering) u otros propósitos.

```bash
wget --no-verbose https://www.google.com/humans.txt && cat humans.txt

Google is built by a large team of engineers, designers, researchers, robots, and others in many
different sites across the globe. It is updated continuously, and built with more tools and
technologies than we can shake a stick at.
```

# Enumerar aplicaciones en un WebServer
Dentro del scope con el que se esté trabajando en un test, es necesario identificar todas las aplicaciones y servicios que están corriendo del del servidor(es) que entren en el scope de las pruebas.
A menudo las aplicaciones que se encuentren serán más fáciles de atacar, ya que están peor securizadas debido a la percepción de que solo se usan de forma "interna". Ya se esté trabajando con una IP o una lista de ellas, es crucial identificar todas las aplicaciones que entren en el scope establecido.

## Metodología
Hay 3 factores que determinan cuántas aplicaciones están relacionadas con un nombre DNS (o una IP).
### Diferente URL base
Normalmente el "punto de entrada" de una página es en la raíz (`/`), sin embargo, esto no es obligatorio y podría haber varias aplicaciones diferentes dentro de un mismo dominio/IP.
- `www.ejemplo.com/app1/`
- `www.ejemplo.com/app2/`
- `www.ejemplo.com/app3/`
En este caso, la raíz podría ser una página irrelevante, y las tres aplicaciones principales están escondidas si el tester no sabe de su existencia y nombre específico (aunque se pueden encontrar fuzzeando).

En caso de que los nombres para las aplicaciones sean non-standard, puede ser virtualmente imposible encontrarlas, por ejemplo, si hubiese un `bocatadechorizo.ejemplo.com`, a nadie se le pasaría por la cabeza probar ese nombre. Sin embargo, hay técnicas que permiten "adivinar" estas direcciones.
#### Directory browsing
Si el webserver es vulnerable y permite directory browsing, se podrían encontrar estas aplicaciones.
#### Referencias externas
Si los enlaces en cuestión están referenciados en otros lugares (documentación, otroas páginas, redes sociales...) O indexados por crawlers ([[1.1InfoGathering#Search Engines]]) se podrían encontrar con operadores de búsqueda (`site:www.ejemplo.com`)
#### Fuzzing
Evidentemente, buscar en el server URLs de aplicaciones que no estén publicadas es crucial, esto puede revelar interfaces administrativas, webmail servers... Esto se puede conseguir o bien probando con educated guesses o con herramientas.
### Non-standard ports
Aunque hay puertos muy comúnmente utilizados para alojar distintos tipos de servicios, esto no es obligatorio y todos ellos (HTTP, HTTPS, SMB, FTP...) podrían estar alojados en cualquiera de los puertos desde el 0 hasta el 65535.

La utilización de scanners o simplemente el siempre necesario escaneo con [[Nmap]] es suficiente para revelar todos los puertos expuestos de la máquina objetivo.
### Virtual hosts
[[DNS 101]] permite permite que una IP esté asociada con más de un nombre. Por ejemplo, la IP `192.168.1.100` podría estar asociada con: `www.ejemplo.com`, `soporte.ejemplo.com`, `correo.ejemplo.com`... No es necesario que todos los nombres pertenezcan al mismo dominio DNS. Esta relación 1-to-many puede ser utilizada para servir distinto contenido usando virtual hosts.

Hay una serie de técnicas que pueden ser utilizadas para para identificar nombres DNS con una determinada IP.

#### DNS Zone Transfers
#### DNS Inverse Queries
#### Web DNS searches
[Netcraft tool](https://searchdns.netcraft.com/?host)
#### Reverse IP services
- Bing: `ip:x.x.x.x`
- [DNSstuff toolset](https://www.dnsstuff.com/freetools)
#### Search engines
Conforme se van descubriendo direcciones, es ideal utilizar las técnicas de [[1.1InfoGathering#Search Engines]] para continuar perfilando la infraestructura.

## Tools
[[nslookup]], [[1.1InfoGathering#Search Engines]], [[Nmap]], [[!nikto]], [[1.1InfoGathering#Virtual hosts]]

# Contenido de la web
Recopilar y analizar todo el contenido que esté disponible dentro del scope para comprender mejor como se comporta y funciona la aplicación, ver si hay log/error/debug files expuestos y si hay comentarios que revelen info sensible.
## Metodología
### Revisar comentarios y metadata
```
<!-- Use the DB administrator password for testing: f@keP@a$$w0rD -->
```

Puede llegar a encontrase algo así, no es tan raro como cabría esperar.
### Identificar y recopilar los archivos JavaScript
Los developers a menudo se dejan credenciales y otra info jugosa hardcodeada en texto o plano o con criptografía débil en este tipo de archivos, puede haber: API keys, IPs internas, rutas sensibles, credenciales...

```js
const myS3Credentials = {
accessKeyId: config('AWSS3AccessKeyID'),
secretAcccessKey: config('AWSS3SecretAccessKey'),
};
```

Si se encuentran credenciales, hay que testear si tienen restricciones o están caducadas, y en caso de dar acceso se puede (si entra en el scope) identificar de que maneras y a que niveles se puede explotar ese acceso.
### Identificar source map files
Este tipo de archivos se cargan al abrir las DevTools, también se pueden acceder cambiando la extensión de un archivo `.js` a `.map`

Analizar estos archivos puede proporcionar info adicional sobre el funcionamiento interno de la página

## Tools
[[wget]], DevTools/view source, [[curl]], Burp, waybackurls

[Keyhacks](https://github.com/streaak/keyhacks) --> KeyHacks shows methods to validate different API keys found on a Bug Bounty Program or a pentest.

# Identificar los puntos de entrada de la app
Esta fase consiste en enumerar, documentar y representar la superficie de ataque, identificando las áreas potencialmente vulnerables. El objetivo es identificar los puntos e entrada e inyección a través del análisis de solicitudes y respuestas.

## Metodología
Es importante tener una compresión rica de como se comportan los protocolos y prestar atención a las solicitudes HTTP, especialmente `GET` y cuando `POST` se utiliza para enviar parámetros a la app, así como otros métodos de servicios REST.
### Requests
- Identificar los lugares donde se usa `GET` y `POST`
- Identificar los parámetros enviados `POST`
	- Especial atención a los parámetros `hidden`
	- Identificar **todos** los parámetros que son procesados, incluidos encodings, cifrado y hashes
- Identificar los parámetros usados en una petición `GET`
	- Especial atención a los parámetros pasados por URL (normalmente tras un `?`: `ejemplo.com?param=param`)
	- Identificar los parámetros de la query string, normalmente en pares `foo=bar`, recalcar que puede haber varios parámetros concatenados con símbolos como `&`, `\~`, `:`...
- Prestar atención a otros Headers como `debug=false`
### Responses
- Identificar cuándo se setean nuevas Cookies (`Set-Cookie` header), se modifican modifican o añaden.
- Identificar redirects (300); códigos 400, en particular los 403 y errores de servidor (500)
- Identificar Headers que puedan resultar en una mayor superficie de ataque, por ejemplo, `Server: BIG-IP` indica que el sitio está [load balanced](https://www.youtube.com/watch?v=LQuuoHTyYz8&pp=ygUObG9hZCBiYWxhbmNpbmc%3D).

## Tools
[Attack surface detector](https://owasp.org/www-project-attack-surface-detector/), ZAP, BURP


# Mapear los execution paths
Con el objetivo de seguir dibujando una imagen cuánto más precisa y detallada de la infraestructura, el objetivo de esta fase es identificar y mapear la aplicación, en específico sus workflows.
En una aplicación normal, es prácticamente imposible testear cada camino, opción y parámetro, especialmente en black-box testing, pero es clave documentar rigurosamente los que sí se han podido testear.

En general, crear apoyos visuales es un recurso genial para retener mejor la información y tener una interfaz con la que visualizar la infraestructura e incluso dejar notas para documentar el progreso y ubicar las zonas vulnerables. Este consejo aplica en general pero es especialmente útil en esta etapa.
### Code Review
En una auditoría grey o white-box, revisar directamente el código fuente es una opción evidente.
### Automatic Spidering
Las herramientas automatizadas (más aún conforme más avanza el ML) puede ser una herramienta poderosa que se encarga del trabajo tedioso y repetitivo de probar cientos de miles de recovecos en la app, un testeo manual exhaustivo siempre será de mayor calidad, pero lanzar un spidering es buena práctica.

## Tools
ZAP (Spider, AJAX spider, OpenAPI support), diagram.io, Excalidraw


# Fingerprint WebApp framework
En el panorama actual del desarrollo web, la utilización de paquetes, frameworks, y proyectos de todas las formas y colores son el pan de cada día a la hora de construir sitios web. Identificar las tecnologías utilizadas en la página objetivo puede resultar muy útil para la explotación posterior de vulnerabilidades específicas de estas tecnologías (WordPress, Next.js, Django...)

## Metodología
Hay que analizar las siguientes ubicaciones a la hora de identificar:
- HTTP headers
	- `X-Powered-By:`
	- `Server:`
	- `X-Generator:`
- Cookies
	- [Cookiepedia](https://cookiepedia.co.uk/): "...[all about cookies](https://cookiepedia.co.uk/all-about-cookies), the [types of data](https://cookiepedia.co.uk/types-of-cookies) they collect, and the websites that use them."
- Código fuente
	- `<head>`
	- `<meta>`
	- Footer
- Ciertos archivos y carpetas específicos
	- `wp-config.php` delata la utilización de WordPress como CMS, por ejemplo.
	- Dirbusting
	- `robots.txt`
- Extensiones de archivos
	- `.php` = PHP, `.aspx` = ASP.NET, `.jsp` = Java Server
- Mensajes de error

### General markers
- `%framework_name%`
- `powered by`
- `built upon`
- `running`

## Tools
[[whatweb]], Wappalyzer (browser extension)


# Mapear la arquitectura de la app
El objetivo de este punto (similar al anterior) es el de generar un diagrama o mapa de las redes y arquitectura la aplicación, para tener una comprensión robusta y bien documentada y un apoyo visual de todas las áreas que han de ser testeadas.

Hay que tener en cuenta que algunas aplicaciones son sencillas y consisten de un servidor único, pero hay casos mucho más complejos con múltiples servidores separados por firewalls, zonas de redes...
Esta información es sencilla de representar si se nos da (en una prueba white o gray-box), pero en un testeo a ciegas puede ser un auténtico reto. A raíz de las pruebas se van anotando los descubrimientos, un tester debe preguntarse: ¿Este servidor está protegido por un firewall? ¿Es un firewall stateful o un ACL?

A la hora de identificar los distintos recursos y sus barreras la experiencia es muy útil, pero tener un buen toolset y saber como comparar los resultados de ciertas pruebas en Internet ayuda a tener una imagen clara de la infraestructura a testear.
