# Testear las definiciones de los roles
Las aplicaciones tienen distintas funcionalidades y servicios pensados para diferentes tipos de usuarios (p.ej: Cliente, administrador, helpdesk), estos roles tienen diferentes permisos para invocar funciones o acceder a recursos.

## Metodología
Los objetivos de esta fase son:
- Identificar y documentar los roles que se están utilizando
- Intentar cambiar o acceder a otro rol
- Auditar la granularidad de los roles y el sistema de permisos
### Identificar los roles
- Documentación
- Explicación de los desarrollados (gray/white-box)
- Comentarios en SC
- Fuzzing
	- Cookies (p.ej:`role=Admin` o `isAdmin=true`)
	- Variables (`Role:manager`)
	- Dirs o archivos ocultos (`/admin`, `/mod`)
	- Nombres convencionales (`admin`, `root`)
### Intentar cambiar de rol
En base a la información obtenida en el paso anterior, tratar de modificar valores para acceder a roles distintos.

# Testear el proceso de registro de usuarios
Esta fase pretende auditar el registro, validar su funcionamiento y verificar que los estándares de identidad se ajustan a las políticas de seguridad.

## Metodología
- ¿Cualquiera puede registrarse?
- ¿Los procesos se verifican de forma automatizada en base a criterios X o los verifica un humano?
- ¿Puede la misma persona o entidad registrarse múltiples veces?
- ¿Puede un usuario registrarse para un rol X?
- ¿Que prueba de identidad se requiere?
- ¿Cómo se verifica la identidad requerida?
Validar el proceso de registro
- ¿Se puede crear o falsear una identidad?
- ¿Se puede manipular el tránsito de la info de identidad durante el registro?


# Testear el proceso de suministro de cuentas
Verificar que tipos de cuentas pueden suministrar otras cuentas y de qué tipo son estas.

## Metodología
- ¿Hay alguna verificación, vetado y autorización para suministrar cuentas?
- ¿Hay alguna verificación, vetado y autorización para des-suministrar cuentas?
- ¿Un administrador; puede crear otros admins o solo usuarios?
- ¿Puede un administrador producir cuentas con más privilegios que la suya propia?
- ¿Puede un administrador o usuario auto-vetarse?
- ¿Cómo se gestionan los archivos de cuentas vetadas? ¿Se eliminan? ¿Se transfiere su propiedad?


# Auditar enumeración de cuentas/cuenta 'adivinable'
En esta fase se pretende averiguar si es posible generar o recopilar una lista de usuarios válidos estudiando los mecanismos de autenticación de la app. Se debe:
- Revisar los procesos relacionados a la autenticación
- Crear listas (si es posible) en base a analizar el comportamiento

## Metodología
### Respuestas HTTP
1. Documenta el comportamiento de la app al proporcionar credenciales válidas (validUser:validPass)
2. Documenta el comportamiento de la app al proporcionar username válido y contraseña inválida (validUser:badPass)
3. Documenta el comportamiento de la app al proporcionar un usuario no existente (badUser:badPass)
En base a la información ganada en estos pasos, evaluar si es posible enumerar usuarios (p.ej: Si la app responde con algo como 'Contraseña inválida para el usuario `jdoe`' se pueden enumerar usuarios)

### Analizar el código de error de la página login
A veces, información útil puede ser leakeada por los errores de la app.
### Analizar URLs y redirecciones
Imagina un caso en el que `badUser:badPass` y `validUser:badPass` generan, respectivamente estas respuestas.
```
http://www.foo.com/err.jsp?User=baduser&Error=0
```

```
http://www.foo.com/err.jsp?User=gooduser&Error=2
```

Gracias al valor del campo `User=` y `Error=` se puede deducir que es posible enumerar usuarios.
### Probar URIs
Por ejemplo, si visitamos:
```
ejemplo.com/user/manolito
```

Y la respuesta es `404`, pero al visitar:

```
ejemplo.com/user/paquito
```

Recibimos un `403 Forbidden`, se deduce que es posible la enumeración de usuarios.
### Analizar los títulos de webpage
Buscar cosas como `Invalid user` o `Invalid authentication`
### Analizar mensajes de una funcionalidad de recuperación
Por ejemplo, si solicitamos un reset de contraseña, analizar los mensajes.
```bash
Invalid username: email address is not valid or the specified user was not found.
----
Valid username: Your password has been successfully sent to the email address you registered with.
```
### Friendly 404
A veces al solicitar un recurso inexistente se devuelve un `200` con contenido como una imagen en lugar de un 404.
### Response times
Analizando los tiempos que tarda en contestar la aplicación se puede deducir si un usuario existe, especialmente en workflows que implican un servicio externo (como enviar un correo al solicitar un reset de contraseña)
