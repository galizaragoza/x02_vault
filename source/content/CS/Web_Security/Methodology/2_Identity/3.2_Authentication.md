# Credenciales sobre canales no encriptados
En esta fase se audita la utilización de criptografía para la info en tránsito, un cliente puede enviar o recibir información en distintas situaciones y esta información debe estar protegida.

## Metodología
El propósito de esta fase es verificar que las credenciales que viajan en la aplicación están correctamente encriptadas.

1. Utilizamos un proxy como ZAP o Burp
2. Desactivamos toda opción del navegador que favorezca HTTPS sobre HTTP, para esto se puede utilizar otro navegador o un [perfil](https://support.mozilla.org/en-US/kb/profile-manager-create-remove-switch-firefox-profiles)

En el tráfico capturado en las pruebas listadas abajo, se examina el contenido en busca de:
- Passphrases o contraseñas
- Tokens (normalmente en cookies)
- Códigos de confirmación, reset de contraseña...

### Login
La idea es tratar de iniciar sesión con credenciales válidas mediante HTTP, para que la aplicación pase la prueba, la petición final debería haberse pasado a HTTPS.
- Las credenciales deberían estar cifradas
- Si el servidor devuelve una cookie de sesión, debería llevar el atributo `Secure`
### Creación de cuenta
Como en el test de login, tratamos de forzar una conexión HTTP en la creación de cuenta, los mismos criterios aplican.
### Reset, cambio de contraseña y otras acciones sobre la identidad
- Funcionalidades que envían credenciales olvidadas o unas nuevas
- Funcionalidades que permiten editar credenciales
- Funcionalidades que redirigen a autenticación con otro servicio (pago con tarjeta de crédito)
### Acceder a recursos autenticado
La idea es probar a acceder a recursos variados (incluso los que no requieren estar logueado para ser accedidos) forzando HTTP, buscando leaks de credenciales no cifradas.


# Credenciales por defecto
Esto es bastante autodescriptivo, conforme las aplicaciones involucran cada vez más frameworks, servicios, paquetes y microservicios, hay muchas 'entidades' comunicándose entre sí y muchos humanos que necesitan credenciales para acceder a distintos servicios. Por distintas razones los desarrolladores a menudo dejan las credenciales por defecto, el objetivo de esta fase es la siguiente:
Tras haber identificado las tecnologías subyacentes, investigar sus credenciales por defecto y probarlas.

Esto aplica tanto a credenciales por defecto específicas de un servicio X, como a credenciales 'estándar por defecto'
### Testear defaults de nuevas cuentas
Similar a [[3.1_IdentityManagement#Adivinar usuarios]], tratar de identificar patrones en contraseñas generadas por el servidor y ver si existen.


# Mecanismos de lock out débiles
Las aplicaciones han de tener un mecanismo de lockout que logre un balance entre dar robustez a la seguridad a la página pero a la vez no interferir en la experiencia bloqueando a un usuario legítimo de acceder a su cuenta. El objetivo de esta fase es evaluar la capacidad del mecanismo de de mitigar ataques de fuerza bruta, así como la capacidad de desbloquear cuentas no autorizadas.

## Metodología
1. Intentar iniciar sesión con una contraseña incorrecta 3 veces
2. Al cuarto intento poner la contraseña correcta
3. Repetir incrementando el número de intentos N veces
4. Al bloquear la cuenta sabemos la cantidad de intentos que la aplicación admite
5. Entonces, probar tras 5 minutos, y ver si se ha desbloqueado
6. Probar de nuevo tras 10 minutos, y así sucesivamente hasta averiguar la duración del bloqueo
### CAPTCHA
Los captcha puedes ser medidas protectoras frente a ataques bruteforce, pero tienen su vulnerabilidades
- Retos sencillos, como aritméticos o un set de preguntas limitado
- CAPTCHA que mira la respuesta HTTP y no la resolución del reto
- Lógica de servidor del CAPTCHA que evalúa true por defecto
- Resultado del CAPTCHA que no se valida en el servidor
- CAPTCHA sin validación/sanitización adecuada

Para evaluar el CAPTCHA

1. Evaluar la dificultad y la capacidad de automatizar la resolución del reto
2. Tratar de avanzar sin resolver el reto
3. Tratar de avanzar con una respuesta intencionalmente incorrecta
4. Intentar avanzar sin resolver el reto a través de un proxy
5. Fuzzear los inputs del CAPTCHA con caracteres especiales y payloads comunes
6. Evaluar si la solución del CAPTCHA es el alt-text de un archivo o un valor en un campo oculto
7. Intentar proporcionar respuestas previamente evaluadas como correctas
8. Comprobar si eliminar las cookies es viable para bypassear el CAPTCHA
9. Si es un proceso multipaso, intentar saltarse uno o varios pasos
10. Probar en rutas alternativas que no tengan CAPTCHA (por ejemplo endpoints para dispositivos móviles)

# Bypasses de autenticación
## Metodología
### Direct Page Request
Navegar directamente a una página en la que se debería estar autenticado podría darnos acceso si no se han implementado bien los controles.
### Modificación de parámetros
Por ejemplo, una redirección tras el login que nos de un valor así:
`ejemplo.com/secreto?autenticado=si`, si se puede manipular el valor de `autenticado` podría ser posible aceder al recurso X.
### Predicción de ID de sesión
Si la generación de IDs de sesión es secuencial o predecible de alguna forma se puede robar la identidad de un usuario adivinando la ID.

# Debilidades del Cache del Navegador
- Evaluar si la aplicación almacena info sensible en el lado del cliente
- Evaluar si se puede dar acceso sin autorización
## Metodología
### Historial
1. Almacenar algún tipo de info sensible y cerrar sesión
2. Clicar en el botón de regresar del navegador
3. Comprobar si la información sensible se muestra sin autenticación
Si se puede acceder a páginas previas pero no acceder a nuevo contenido, entonces el problema es con el historial del navegador, no de autenticación. Si las páginas contienen info sensible la aplicación le ha permitido al navegador almacenarla, esto se evita:
- Mediante HTTPS
- Con el Header `Cache-Control: must-revalidate`
### Cache
Para evaluar correctamente si se protege la información de ser cacheada, se consumen ciertos recursos de la página con un proxy y se analizan los headers de las respuestas, debería haber:
- `Cache-Control: no-cache, no-store`
- `Expires: 0`
- `Pragma: no-cache`
- `Cache-Control: must-revalidate, max-age=0, s-maxage=0`

# Política de contraseñas débil
Testear la robustez de las contraseñas frente a ataques de diccionario o fuerza bruta, evaluando su longitud, reusabilidad, complejidad y longevidad.
## Metodología
1. ¿Que caracteres se permiten/prohíben, se requiere al usuario emplear caracteres especiales y distintos sets (mayus, min, números, car. especiales)?
2. ¿Cada cuánto puede un usuario cambiar su contraseña, cuán rápido puede cambiarla tras un intento?
3. ¿Cada cuánto se rotan las contraseñas?
4. ¿Cómo de a menudo se pueden reutilizar contraseñas?
5. ¿Cómo de distinta debe ser una contraseña de la anterior?
6. ¿Se previene de alguna forma que el usuario utilize su username u otra info fácilmente adivinable como `pepePerez1998`?
7. ¿Cuáles son las longitudes mínimas y máximas?
8. ¿Es posible usar contraseñas débiles como '1234' o 'Contraseña1'

# Autenticación más débil en canales alternativos
En muchas organizaciones hay múltiples aplicaciones para distintos casos, que se evalúan en base a ciertas cosas como el locale, la ubicación, el tipo de dispositivo... Y muestran distintas aplicaciones para móvil, otros países...
## Metodología
- Identificar si existen canales alternativos
- Evaluar la seguridad de dichos canales
### Tabla de mecanismos
Realizar una tabla que liste los canales y sus métodos
### Realizar los test anteriores/posteriores
Evaluar la seguridad de estos canales con todos los métodos vistos y por ver.
